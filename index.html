01 / Incident Response

Incident management workflow

Follow a consistent investigation process instead of jumping straight to a possible fix.

  1. 1. Identify

    Record the symptom, start time, affected service, and evidence.

  2. 2. Assess

    Determine business impact, scope, urgency, and severity.

  3. 3. Investigate

    Correlate logs, recent changes, dependencies, and error patterns.

  4. 4. Resolve & verify

    Apply an approved fix, test recovery, and document the outcome.

Example: application returns HTTP 500

Initial checks

  • Confirm the affected endpoint, users, and time window.
  • Check application and web-server logs around the failure.
  • Review recent deployments, configuration changes, and dependencies.
  • Check database connectivity and dependency health.
  • Escalate with timestamps, correlation IDs, and sanitized evidence.
Do not assume the HTTP 500 error is caused by the database. Establish the failure point from logs and correlated evidence. Avoid exposing credentials, tokens, or customer data in incident reports.
Case Study 01 / Production Support

Resolving an HTTP 500 incident

A simulated investigation showing how an application support engineer moves from an initial symptom to an evidence-based resolution.

Incident summary

Following a routine application deployment, users begin receiving HTTP 500 responses from an API endpoint. The application process is running, but requests that require database access are failing.

Business impact

  • Users cannot complete the affected operations.
  • Support tickets and failure rates increase.
  • Other endpoints must be checked to establish the scope.

Investigation timeline

  1. Detect: Confirm the first reported failure, affected endpoint, timestamps, error rate, and impacted users.
  2. Assess: Check whether the incident is isolated to one endpoint or affects multiple application functions.
  3. Investigate: Correlate application logs with the deployment time and inspect database connectivity and configuration.
  4. Identify: The illustrative evidence indicates that the new deployment references an incorrect database host.
  5. Resolve: Correct the configuration through the approved change process and restart or reload the service if required.
  6. Verify: Confirm successful database connections, successful API responses, and recovery of the affected operation.

Example log evidence

2026-10-08 09:14:22 ERROR Database connection failed
2026-10-08 09:14:22 ERROR Host=db-primary.invalid
2026-10-08 09:14:22 ERROR RequestId=demo-7f31
2026-10-08 09:14:23 INFO  HTTP POST /api/orders -> 500

These log entries are fictional examples for demonstration. In a real incident, correlate the request ID and timestamps with the actual application and database logs.

Root cause

In this simulated scenario, a database host configuration was incorrect after deployment. The API could not establish the required database connection, and affected requests returned HTTP 500.

Corrective actions

  • Restore the correct database endpoint using approved configuration.
  • Verify network access, credentials, and database availability.
  • Test the affected API operation using an authorized test request.
  • Monitor error rates and application logs after recovery.
  • Communicate service status and document the incident.

Preventive actions

  • Validate required configuration before deployment.
  • Add database connectivity checks to deployment verification.
  • Alert on abnormal HTTP 500 rates and database connection failures.
  • Document configuration rollback and recovery procedures.
Key lesson: an HTTP 500 response identifies a server-side failure, not its root cause. The diagnosis must be supported by logs, configuration checks, and reproducible evidence.
02 / Server Diagnostics

Linux troubleshooting

Start with visibility into system health before making configuration or service changes.

Essential diagnostic commands

Check disk space

df -h

Check memory usage

free -h

Inspect CPU and running processes

top

Check a service status

systemctl status SERVICE_NAME

Review recent service logs

journalctl -u SERVICE_NAME -n 100 --no-pager

Check listening TCP ports

ss -lntp
Replace SERVICE_NAME with the actual service name. Some commands require elevated privileges. Review permissions and operational procedures before running privileged commands.
03 / Database Investigation

SQL diagnostics

These PostgreSQL examples use illustrative table and column names. Adapt them to your authorized database schema.

Find recent failed transactions

SELECT
    transaction_id,
    status,
    created_at
FROM transactions
WHERE status = 'FAILED'
  AND created_at >= CURRENT_TIMESTAMP - INTERVAL '24 hours'
ORDER BY created_at DESC
LIMIT 100;

Count transactions by status

SELECT
    status,
    COUNT(*) AS transaction_count
FROM transactions
WHERE created_at >= CURRENT_TIMESTAMP - INTERVAL '24 hours'
GROUP BY status
ORDER BY transaction_count DESC;

Investigation checklist

  • Confirm the correct environment and reporting time zone.
  • Check the transaction reference and current status.
  • Compare timestamps across relevant system logs.
  • Review duplicate references and related records.
  • Use approved access controls and read-only queries where possible.
These queries are examples, not production-ready statements for an unknown schema. Confirm table names, column types, indexing, permissions, and data-retention requirements first.
04 / Integration Support

API troubleshooting

Treat response codes as clues, then validate them against the request, logs, and service behavior.

Common HTTP status codes

  • 400 Bad Request: inspect request format and validation errors.
  • 401 Unauthorized: verify authentication and token validity.
  • 403 Forbidden: inspect permissions and access policies.
  • 404 Not Found: confirm endpoint, route, and resource identifier.
  • 429 Too Many Requests: inspect rate limits and retry guidance.
  • 500 Internal Server Error: investigate server-side logs and exceptions.
  • 502 / 503 / 504: investigate upstream availability, gateway behavior, and timeouts.

Example request

curl -i --max-time 15 \
  "https://api.example.com/health"

This inspects the response headers and body while limiting the request duration. Replace the placeholder URL with an authorized endpoint.

Never paste API keys, bearer tokens, passwords, or sensitive customer payloads into public repositories or shared screenshots.
05 / Transaction Support

Payment operations

A failed payment requires investigation of the complete transaction lifecycle, not just the displayed error.

Failed payment investigation checklist

  • Record the transaction reference, amount, currency, and timestamp.
  • Identify the source channel, destination institution, and response code.
  • Determine whether the source account was debited.
  • Check the beneficiary or settlement status.
  • Correlate provider responses with internal application logs.
  • Confirm whether a reversal, settlement, or reconciliation entry exists.
  • Obtain the required authorization before retrying or reprocessing.
  • Verify the final state and communicate the outcome to stakeholders.
Before retrying a payment, verify its current state and the system's idempotency controls. A timeout does not prove that the original transaction failed. Unverified retries can create duplicate payment risks.
