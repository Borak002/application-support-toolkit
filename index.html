01 / Incident Response

Incident management workflow

Use a consistent investigation process instead of jumping straight to a possible fix.

1. Identify

Record the symptom, start time, affected service, and evidence.

2. Assess

Determine business impact, scope, urgency, and severity.

3. Investigate

Correlate logs, recent changes, dependencies, and error patterns.

4. Resolve & Verify

Apply an approved fix, test recovery, and document the outcome.

Example: Application returns HTTP 500

Initial checks

  • Confirm the affected endpoint, users, and time window.
  • Check application and web-server logs around the failure.
  • Review recent deployments, configuration changes, and dependencies.
  • Check database connectivity and dependency health.
  • Escalate with timestamps, correlation IDs, and sanitized evidence.
Do not assume the HTTP 500 error is caused by the database. Establish the failure point from logs and correlated evidence. Avoid exposing credentials, tokens, or customer data in incident reports.
02 / Server Diagnostics

Linux troubleshooting

Start with visibility into system health before making configuration or service changes.

Essential diagnostic commands

Check disk space

df -h

Check memory usage

free -h

Inspect CPU and running processes

top

Check a service status

systemctl status SERVICE_NAME

Review recent service logs

journalctl -u SERVICE_NAME -n 100 --no-pager

Check listening TCP ports

ss -lntp
Replace SERVICE_NAME with the actual service name. Some commands require elevated privileges. Review permissions and operational procedures before running privileged commands.
03 / Database Investigation

SQL diagnostics

These PostgreSQL examples use illustrative table and column names. Adapt them to your authorized database schema.

Find recent failed transactions

SELECT transaction_id, status, created_at FROM transactions WHERE status = 'FAILED' AND created_at >= CURRENT_TIMESTAMP - INTERVAL '24 hours' ORDER BY created_at DESC LIMIT 100;

Count transactions by status

SELECT status, COUNT(*) AS transaction_count FROM transactions WHERE created_at >= CURRENT_TIMESTAMP - INTERVAL '24 hours' GROUP BY status ORDER BY transaction_count DESC;

Investigation checklist

  • Confirm the correct environment and reporting time zone.
  • Check the transaction reference and current status.
  • Compare timestamps across relevant system logs.
  • Review duplicate references and related records.
  • Use approved access controls and read-only queries where possible.
These queries are examples, not production-ready statements for an unknown schema. Confirm table names, column types, indexing, permissions, and data-retention requirements first.
04 / Integration Support

API troubleshooting

Use response codes as clues, then validate them against the request, logs, and service behavior.

Common HTTP status codes

  • 400 — Bad Request: inspect request format and validation errors.
  • 401 — Unauthorized: verify authentication and token validity.
  • 403 — Forbidden: inspect permissions and access policies.
  • 404 — Not Found: confirm endpoint, route, and resource identifier.
  • 429 — Too Many Requests: inspect rate limits and retry guidance.
  • 500 — Internal Server Error: investigate server-side logs and exceptions.
  • 502 / 503 / 504: investigate upstream availability, gateway behavior, and timeouts.

Example request

curl -i --max-time 15 \ "https://api.example.com/health"

This example inspects the response headers and body while limiting the request duration. Replace the placeholder URL with an authorized endpoint.

Never paste API keys, bearer tokens, passwords, or sensitive customer payloads into public repositories or shared screenshots.
05 / Transaction Support

Payment operations

A failed payment requires investigation of the complete transaction lifecycle, not just the displayed error.

Failed payment investigation checklist

  • Record the transaction reference, amount, currency, and timestamp.
  • Identify the source channel, destination institution, and response code.
  • Determine whether the source account was debited.
  • Check the beneficiary or settlement status.
  • Correlate provider responses with internal application logs.
  • Confirm whether a reversal, settlement, or reconciliation entry exists.
  • Obtain the required authorization before retrying or reprocessing.
  • Verify the final state and communicate the outcome to stakeholders.
Before retrying a payment, verify its current state and the system's idempotency controls. A timeout does not prove that the original transaction failed. Unverified retries can create duplicate payment risks.
06 / Operational Excellence

Runbooks & documentation

Document what was observed, what was checked, what changed, and how recovery was verified.

Reusable incident report template

INCIDENT TITLE: DATE / TIME: AFFECTED SERVICE: BUSINESS IMPACT: SEVERITY: SYMPTOMS: ERROR MESSAGE / CORRELATION ID: INVESTIGATION: 1. 2. 3. ROOT CAUSE: RESOLUTION: VALIDATION PERFORMED: CURRENT STATUS: PREVENTIVE ACTIONS: OWNER / ESCALATION TEAM:

Recommended runbook structure

  1. Purpose and scope
  2. Prerequisites and access requirements
  3. Symptoms and impact indicators
  4. Diagnostic commands and expected results
  5. Decision points and escalation criteria
  6. Approved remediation steps
  7. Post-resolution verification
  8. Rollback plan and lessons learned
